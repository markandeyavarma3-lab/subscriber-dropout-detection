CHAPTER 9Serving: the API, explanations and the dashboard

The champion model behind an HTTP API that validates every input, explains every answer, and degrades gracefully instead of failing.

Liveness vs readiness

Two different questions. Liveness (/health): is the process running? If not, restart it. Readiness (/ready): can it serve right now? If not, stop sending it traffic, but don't kill it. A service with no model is alive but not ready. It answers /health, and /predict returns 503 Service Unavailable with a clear message rather than crashing with a 500. Kubernetes uses exactly these two endpoints for its probes.

Input validation

Every request is validated by Pydantic before it reaches the model: required fields present, correct types, values in range (for example, fees 0–10,000), plan type normalised. There's also a cross-field rule: last activity can't be longer ago than the subscription's tenure. Invalid input gets a 422 response naming the field and the problem, never a wrong prediction.

Explanations with SHAP

SHAP (SHapley Additive exPlanations) comes from cooperative game theory. It asks how much each feature contributed to this prediction, compared with the average prediction. For tree models, SHAP's TreeExplainer computes the values exactly, not by approximation.

The key property is additivity: the average prediction plus every feature's contribution equals exactly what the model predicted (in log-odds, the scale the model works in internally). A test in the suite checks this for every row. So the explanation can't disagree with the score, unlike a rule-based explanation that describes the input without knowing what the model did.

Raw SHAP values are per model column, and some concepts span several columns (e.g. tenure_days and tenure_months). The service sums them into ten concepts: recency, engagement, tenure, payments, support, friction, discounts, price, auto-renew and plan. Summing is valid because Shapley values are additive. The strongest concepts, by absolute size, become the explanation. The wording states the actual input: an earlier version said "auto-renew enabled" for a subscriber who had it off, because it followed the direction of the effect rather than the value. That's fixed and tested.

If SHAP isn't available or fails, the prediction is still returned, with a rule-based explanation and "explanation_method": "rules", so a client always knows which kind it got. An explanation is a feature of a prediction, never a precondition for one.

The live MLOps pipeline (the Overview)

The rest of the project runs its pipeline on a schedule, which is invisible in a 15-minute demo. The Overview makes it visible. Each click on Run pretends it is a specific day in early 2017 and does exactly what the nightly pipeline would have done that day, on the real KKBox data in Postgres:

StageWhat happens
1 · New data arrivesCounts the rows that landed in the warehouse since the last replayed day (listening days, subscription events, payments)
2 · Build featuresThe project's point-in-time feature code, for every cutoff the model may train on, on a fixed sample of 50,000 subscribers. Snapshots are cached, so a cutoff is only built once
3 · ValidateRefuses to train on impossible data: activity before signup, one-class test sets, implausible churn rates
4 · Check driftPSI of the new month against the serving model's training profile (skipped on the first month: nothing to compare against)
5 · TrainThe project's own training pipeline on every month known so far
6 · EvaluatePR-AUC and ROC-AUC on the newest month whose labels are complete, which training never saw
7 · GateThe same promotion gate as production: the challenger must beat the champion's PR-AUC, on the same test month, by at least 0.005
8 · Go liveIf promoted, the API loads the new model and the very next /predict uses it. The run is logged to MLflow under its own experiment (subscriber-dropout-live-replay) and model name (subscriber-dropout-live), and the @champion alias moves

Three months are replayed: 1 Jan 2017, 31 Jan 2017 and 28 Feb 2017. Each one trains on everything before it, including the previous month's test month. On the real data, the result isn't scripted: month 1 is promoted (there is no champion yet), month 2 is rejected (0.0475 vs 0.0474, well inside the 0.005 margin), and month 3 is promoted (0.0568 vs 0.0489), with moderate drift in last-activity days. Restore original model stops the replay and puts the tested production model back.

Why it is honest

No future data. A training label covers the 30 days after its cutoff, so every cutoff a replayed day uses must end on or before that day. A test checks this for every month in the schedule.

Its own lineage. The replay is gated against its own champion, never against the production model. Production was trained on these very months and would win unfairly.

It never blocks serving. The replay runs in a separate process. The API only reads its state file, so predictions keep flowing during a run (a full walkthrough in the containers had zero failed health checks).

Smaller, so it is quick. 50,000 subscribers instead of 6.8 million, so a month takes about 30 seconds. That's why its PR-AUC (about 0.057) is below production's (0.073).

"What would change it": counterfactual levers

SHAP says what the model leaned on. It doesn't say what a retention team could do. So the dashboard sends real second requests to the model, each with one field changed, and shows the new probability. For the at-risk preset:

Lever60.4% becomes
Turn auto-renew off0.24%
Stop discounting0.79%
Bring them back this week31%
Double their listening53%

These are the model's own answers, not inferences. The two fields that are always zero in KKBox (tickets, payment failures) are deliberately never offered as levers, because they'd promise an action that changes nothing.

The live drift test

The Monitoring tab builds 400 plausible subscribers from the presets, then a second "disengaged" copy: sessions cut to near zero and last activity pushed back 45 days. It sends both to /monitoring/drift and compares. The detector ranks exactly the two features that were changed at the top, while the other seven move by less than 0.5. It's an instrument test: proof the detector responds to a change we control.

Say this

"The API validates every input and returns a probability, a risk band and the reasons. The reasons are SHAP values, which add up exactly to the prediction, so the explanation can't contradict the score. The dashboard also asks the model what would change the outcome: each lever is a real second prediction with one field changed. And if the model or the explainer fails, the service degrades: a 503 or a rule-based explanation, never a crash."

CHAPTER 10Streaming inference with Kafka

Scoring events as they happen, without losing data and without letting one bad message stop the pipeline.

Why streaming as well as an API

The API answers when asked. But subscriber events (a payment, a plan change, a quiet week) happen continuously, and the business wants a fresh risk score when they do, not only when someone remembers to ask. A stream scorer consumes events as they arrive and publishes scores for other systems to act on.

The setup

PieceValue
BrokerRedpanda (Kafka-compatible), one container, port 19092
Input topicsubscriber-events
Output topicsubscriber-scores
Dead-letter topicsubscriber-scores-dlq
Consumer groupsubscriber-scorer
Batch sizeup to 200 messages per poll
MetricsPrometheus endpoint on port 8001

The consume → score → produce loop

  1. Poll a batch of up to 200 messages from subscriber-events.
  2. Parse and validate each one with the same schema the API uses.
  3. Score the valid ones in a single batch call to the same prediction code the API uses.
  4. Publish each score to subscriber-scores, keyed by subscriber (so one subscriber's scores stay in order in one partition).
  5. Send each invalid message to subscriber-scores-dlq, with the reason and the original payload kept verbatim.
  6. Wait for the broker to confirm the writes (acks=all), and only then commit the input offsets.

Delivery guarantee: at-least-once

Offsets are committed only after the scores are safely written. If the scorer crashes between producing and committing, it re-reads those messages on restart and scores them again: a duplicate, never a loss. That's at-least-once delivery. Auto-commit is switched off on purpose: it would acknowledge messages whose scores never reached the output topic, which is the one way this design could lose data. Duplicates are harmless here, because re-scoring the same subscriber gives the same score.

The dead-letter queue

A poison message (malformed JSON, a missing field, an impossible value) would crash a naive consumer. Worse, the consumer would restart, read the same message again and crash again: the classic poison-pill loop that takes a pipeline down for good. Here a bad message goes to the dead-letter topic with the reason attached, and the batch carries on. Every message ends up in exactly one place: scored, or dead-lettered with a reason.

One exception is deliberate. If the model itself is unavailable, messages are not dead-lettered, because that would throw away perfectly good data over a temporary problem. The batch fails, offsets aren't committed, and the messages are retried.

CI proves all of this: the streaming job sends deliberately broken messages and checks they land in the dead-letter topic while the good ones are scored.

Say this

"The stream scorer reads events from Kafka, scores them, and writes the scores back. Offsets are committed only after the scores are safely written, so it's at-least-once: a crash causes a duplicate, never a loss. A malformed message goes to a dead-letter topic with the reason, so one bad message can't take the pipeline down. CI sends poison messages to prove it."

CHAPTER 11Monitoring, drift and alerting

A model that was good at launch can quietly get worse. This chapter covers how the system notices.

Why models need monitoring

Ordinary software fails loudly: it crashes or returns errors. A model fails quietly. It keeps returning confident probabilities while the world it was trained on changes underneath it: prices change, a competitor launches, listening habits shift. Nothing errors. The predictions just get steadily worse. Monitoring exists to make that visible.

The monitoring stack

ComponentRole
prometheus-clientThe API and the stream scorer expose counters, histograms and gauges
PrometheusPulls (scrapes) those metrics every 15 seconds, stores the history, and evaluates the alert rules
AlertmanagerReceives firing alerts, groups them, routes them by severity, and suppresses redundant ones
GrafanaThe dashboard, provisioned from a JSON file in the repository

Prometheus pulls rather than having services push. The monitoring system decides what and how often to collect, and a service that stops answering is itself a signal: its up metric drops to 0.

What is measured

  • Traffic: predictions per second by risk band and by component (API or stream), and the score distribution (median, p90, p99).
  • Serving state: model loaded, which source it was served from, the decision threshold, flagged rate, and the shift of the live mean score from the training mean.
  • Pipeline: time since the last run, whether it needs attention, the last promotion decision, the drift verdict, and PSI per feature.
  • Decision quality: calibration error, fairness pass/fail and ratios, savings available, and capacity.
  • Shadow scoring: active or not, agreement rate, outreach change, divergence, latency and errors.

Drift detection with PSI

The Population Stability Index compares two distributions of one feature: training ("expected") and live ("actual").

  1. Split the training values into 10 bins (by quantile, so each holds about 10% of training data). The bin edges are saved in reference_profile.json when the model trains.
  2. Put the live values into the same bins.
  3. For each bin, compare the live share a with the training share e, then add up the terms:
PSI = Σ (a − e) × ln(a / e)

(Shares are clipped at a tiny positive number first, so an empty bin can't cause a division by zero.) If the distributions are identical, every term is zero. The more the live data has moved, the larger PSI grows. Categorical features (plan type) use their categories as bins. The prediction itself is also checked, so a shift in the model's output is caught even when no single input moved much.

PSIVerdictMeaning
< 0.10stableNo meaningful change
0.10 – 0.25moderateWorth watching
> 0.25significantThe population has shifted; consider retraining

Samples under 100 rows are flagged as too small to trust. PSI is noisy on tiny samples, and the response says so rather than reporting a confident verdict.

The real result

The pipeline's drift step was run on the latest real month (February 2017), read from Postgres, against the training distribution (November–December 2016): 7,614 subscribers. Verdict: stable. Every feature's PSI was below 0.06: last activity 0.058, tenure 0.032, sessions 0.007, fee 0.003, plan 0.002. That's a real finding: KKBox's subscriber base didn't shift in those months. The dashboard's drift test is how you show the detector does fire when something changes.

Alertmanager: routing and inhibition

  • Routing by severity: critical goes to an on-call receiver immediately and repeats hourly; warning goes to a review receiver and repeats every 12 hours; info is recorded and repeats daily.
  • Grouping: alerts are grouped by name and component, so ten related alerts become one notification.
  • Inhibition: if the API is down, warnings about it are suppressed, since they're symptoms of the same outage. If no model is loaded, alerts about the score distribution are suppressed.
  • No credentials in the repo: the receivers ship empty. A test fails the build if anything credential-shaped (webhook URLs, routing keys) appears in the config.

Grafana

What looking at it found

With every automated check passing, a screenshot of Grafana showed that things were wrong:

  • Two values in every panel ("LOADED | NO MODEL"). The stream scorer shares the API's metric registry but never updates the API's state gauges, so it exported their defaults. Worse, the alert rules matched those zeros: PipelineStale was firing and ModelNotLoaded was about to, on a healthy system. Fix: every API-state query is scoped to job="subscriber-api", and a test fails if one isn't.
  • "Last promotion: REJECTED" for a run that trained nothing, and "0% agreement" with no challenger. A gauge's default 0 is a claim. These now start as "no value" (NaN) and read "NOT RUN" and "no challenger".
  • Two sections drawn on top of each other, plus a duplicated section. Re-laid out, with a test that no two panels overlap.
