How to use this book

Two halves. Part I explains the whole system, end to end, in the order the data flows. Part II is a question bank: the questions an examiner is likely to ask, with answers.

Read Part I once, slowly. Every chapter ends with a short "Say this" box: the two or three sentences worth being able to say without notes. Part II assumes you've read Part I; its answers are short on purpose.

Learn ideas, not wording. An examiner who hears a memorised paragraph asks a follow-up, and the follow-up is where understanding shows. Many answers in Part II include an "If they push" line: the most likely follow-up and how to handle it.

Every number is real. Figures come from the trained model's own reports (src/models/artifacts/metrics.json), the Postgres warehouse, the CI runs, or measurements taken while building the demo. Where a number is an assumption, such as the cost figures, the book says so.

Be honest about the weak parts

The model is modest, one fairness check fails, and the cost figures are placeholders. Part I says so plainly, and so should you. Examiners respect a student who knows exactly where their system is weak far more than one who claims it has no weaknesses. Chapter 16 lists every limitation.

PART I

The project, end to end

What the system does, how every piece works, and why each design decision was made, from 31 GB of raw CSV to a monitored model served in production.

CHAPTER 1What this project is

A production-style machine learning system that predicts which subscribers of a music-streaming service are about to cancel, explains why, and keeps itself trustworthy after it ships.

The business problem

A subscription business earns money every month a customer stays. When a subscriber cancels ("churns" or "drops out"), that revenue is gone, and winning a customer back costs far more than keeping one. If the business can tell in advance who is likely to cancel, it can act while they're still a customer: a discount, a better-suited plan, a reminder of what they'd lose.

This project answers one question for every subscriber: what is the probability they cancel in the next 30 days? It also says why, and it runs the whole thing the way a real company would: versioned data, a gated model registry, an API, streaming, monitoring, alerting and automated testing.

What "MLOps" means here

Training a good model once is machine learning. MLOps is everything that keeps a model good in production:

  • Data you can trust: validated on the way in, stored so the past can be rebuilt exactly.
  • Training you can reproduce: versioned code, data and parameters.
  • A registry and a gate: a record of every model, and a rule that stops a worse model reaching production.
  • Serving: the model behind an API and a streaming consumer, with explanations.
  • Monitoring: metrics, drift detection and alerts, so a model that is quietly getting worse is noticed.
  • Automation: a scheduled retraining pipeline, and CI/CD that tests the system, not just the code.

The model itself (gradient boosting) is a small part of the codebase. Most of the work, and most of what is worth discussing in a viva, is everything around it.

What was built, in one paragraph

The KKBox churn dataset (real, public, 31.3 GB) is validated, cleaned and loaded into an event warehouse in Postgres. A point-in-time feature pipeline builds training data for any past date without leaking the future. A gradient-boosting model is trained on a time-based split, audited for calibration, cost and fairness, and registered in MLflow. It only becomes the live @champion by beating the current one on PR-AUC. The champion is served by a FastAPI service with SHAP explanations and a dashboard, and by a Kafka stream scorer with a dead-letter queue. Prometheus, Alertmanager and Grafana watch it, with PSI drift detection. A Prefect pipeline retrains on a schedule, DVC versions the data pipeline, and GitHub Actions runs seven jobs on every push, including training on two databases and publishing the Docker image.

CHAPTER 2Architecture

Four stages (data, model, serve, watch) with automation running underneath all of them.

The four stages

StageWhat happensMain code
1 · DataRaw KKBox CSV is validated against a contract, mapped to the warehouse schema, cleaned (orphans dropped, prices normalised) and stored as timestamped events.src/data/external/, src/warehouse/
2 · ModelPoint-in-time features for chosen cutoff dates; time-based split; gradient boosting; decision-quality audit; registered in MLflow and promoted only through the PR-AUC gate.src/features/, src/models/, src/registry/
3 · ServeThe champion model answers HTTP requests (single, batch) with SHAP explanations, powers the dashboard, and scores a Kafka event stream.src/api/, src/streaming/
4 · WatchMetrics scraped by Prometheus, 15 alert rules routed by Alertmanager, a Grafana dashboard, and PSI drift checks against the training distribution.src/monitoring/, deploy/
AutomationPrefect runs ingest, drift, train and gate on a schedule; DVC tracks the pipeline; GitHub Actions tests and publishes on every push.src/orchestration/, dvc.yaml, .github/

Two flows through the system

The training flow (offline, nightly or on demand)

  1. New events land in the warehouse (subscribers, subscription_events, payments, sessions).
  2. The drift step compares recent data against the serving model's training distribution. It runs before retraining (Chapter 12 explains why).
  3. For each cutoff date, the feature pipeline builds one row per subscriber using only data before the cutoff, and a label from the 30 days after.
  4. The model trains on older cutoffs, is tuned on a later one, and is tested on the latest.
  5. The run is logged to MLflow and registered as @challenger. If it beats @champion on PR-AUC by at least 0.005, the champion alias moves to it.
  6. A run report is written; Prometheus exposes it; alerts fire if something needs a human.

The serving flow (online, per request)

  1. A client sends a subscriber's nine features to POST /predict (or events arrive on the subscriber-events Kafka topic).
  2. The service validates the input (types, ranges, and that the last activity isn't longer ago than tenure).
  3. The champion model returns a probability; it's mapped to a risk band (low / medium / high) using the decision threshold.
  4. SHAP computes each feature's contribution; the top reasons become a plain-language explanation.
  5. If a distinct challenger exists, it scores the same request silently (shadow scoring).
  6. Counters and histograms update; Prometheus scrapes them every 15 seconds.

Why Redpanda instead of Apache Kafka?

Redpanda speaks the Kafka protocol, so the code uses a standard Kafka client and would run unchanged against Apache Kafka. It's a single binary with no JVM and no ZooKeeper, which makes it light enough for a laptop and for CI.
