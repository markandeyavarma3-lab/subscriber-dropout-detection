CHAPTER 16Results, limitations and future work

What the system achieves, where it falls short, and what would come next, stated plainly.

What was achieved

  • A complete MLOps system on real data: 31.3 GB raw, 82.8 million warehouse rows.
  • A leak-free training pipeline, verified by tests and by cross-checking two databases row for row.
  • A model about 4.8× better than random at finding churners (PR-AUC 0.073 against a 0.015 base), and well calibrated (ECE 0.004).
  • A registry with a promotion gate, proven in CI to reject an identical challenger.
  • Explained predictions, a dashboard, and streaming inference with a dead-letter queue.
  • Monitoring with PSI drift, 15 alert rules and a Grafana dashboard that reports only true things.
  • Seven CI/CD jobs, 434 tests, and a published, commit-tagged image.
  • The whole stack started and verified with two commands.

Limitations

LimitationWhy, and what it means
The model is modestPR-AUC 0.073, recall 16.8%. KKBox lacks strong signals: two inputs are always zero, and the strict churn definition gives few positives. It's far better than random, but it wouldn't catch most churners.
The fairness audit failsNear-random on the standard plan (949 subscribers). Reported and alerted, not fixed.
Cost figures are placeholdersThe cost-optimal threshold (0.43) is illustrative; the served threshold (0.05) is the F1 choice.
Stricter churn label than Kaggle'sExplicit cancellations only, not quiet lapses. Results aren't comparable with the competition's leaderboard.
Calibration is reported, not appliedIsotonic calibration would shave 0.003 off an already-small error; the pipeline tries it on every run but doesn't switch it on.
Not deployed to a public cloudA 15 GB warehouse plus MLflow, Kafka and Grafana fits no free tier. It runs on Docker locally; Kubernetes manifests are written but not deployed.
Continuous delivery, not deploymentEvery merge publishes a tested image; nothing deploys it to production automatically.
No real challenger yetShadow scoring is built and tested in CI, but idle in the demo.

Future work

  1. Richer features from the full 392-million-row listening log: trends (listening falling week on week), skip rates, completion rates.
  2. Real offer costs, so the threshold is chosen by money rather than F1.
  3. The competition's churn definition, trained alongside this one, to compare.
  4. Address the fairness failure: more standard-plan data, a per-plan threshold, or a model with plan-specific interactions.
  5. Deploy to a managed Kubernetes cluster, with CI deploying each published image to a staging environment.
  6. A real challenger (for example, a model with the new features) running in shadow before any promotion.
  7. A feature store, so training and serving read features from one place.
Say this

"The engineering is complete and tested, and the model is modest: about 5× better than random, because the data lacks strong signals. The fairness audit fails for one plan, the costs are placeholders, and it isn't on a public cloud. I'd add listening-trend features from the full logs, real offer costs, and a managed Kubernetes deployment next."

CHAPTER 17What building it taught

The bugs and surprises, collected in one place. "Tell us about a problem you found" is a classic viva question; each of these is a real, specific answer.

ProblemHow it was foundLesson
ROC-AUC rose while PR-AUC fell on real dataMoving from synthetic to real dataChoose metrics for the class balance you'll actually face
IDs declared 32 characters; real ones are 44Loading real data; Postgres would reject every rowSQLite forgives what Postgres won't; test on the real database
Same-day signups counted as "before" the cutoffComparing SQLite and Postgres snapshots row for rowText-stored dates compare as text; cross-check two implementations
A subscriber cap that didn't cap anythingA single cutoff never finished on real dataA LIMIT on one step doesn't bound the others; push the filter into every aggregate
An explanation that contradicted its input ("auto-renew enabled" when it was off)Reading real explanationsFor booleans, state the value, not the direction of the effect
Preset examples silently inverted (at-risk scored low)Looking at the dashboard after retrainingTests that only compare two outputs can pass while both are wrong
The container served a synthetic modelChecking /model-info in the running stackVerify the deployed artifact, not the code
False alerts, "REJECTED" and overlapping panels in GrafanaA screenshot, with every check greenA passing check isn't a correct screen; look at it
scikit-learn drifted from 1.9.0 to 1.9.1 on rebuildA new checklist item comparing versionsPin what the model depends on
CI red for 17 daysRunning the suite on a fresh cloneA test that passes only on your machine isn't passing
The common thread

Almost every one of these was invisible to the automated tests at the time and found by checking the real thing: the real data, the real database, the running container, the actual screen, a clean checkout. The lasting fixes turned each discovery into a test or a checklist item, so it can't silently come back.
