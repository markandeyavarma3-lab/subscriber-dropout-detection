CHAPTER 12Orchestration and reproducibility

Running the pipeline on a schedule, safely re-runnable, and making any result traceable back to the exact data, code and settings that produced it.

The retraining pipeline

src/orchestration/pipeline.py holds the steps; src/orchestration/flows.py wraps them as Prefect tasks and flows.

StepWhat it doesRetries
1 · IngestBring new events into the warehouse (or leave a populated warehouse alone)2
2 · Assess driftCompare recent data with the serving model's training distribution–
3 · Train and gateTrain a challenger, register it, promote only if it beats the champion1
4 · ReportWrite last_pipeline_run.json, read by Prometheus and alerting–

Why drift is checked before training

Training writes a new reference profile from the latest data. If drift were checked after training, it would compare the latest data with a profile built from that same data, and report "stable" every single time. It would detect nothing, ever. Checked before training, it answers the useful question: has the world moved since the model that's serving now was fitted?

The flows

CommandFlow
python -m src.orchestration.flows runThe full pipeline once, now (make pipeline)
... run --driftSame, after injecting a behavioural shift, to show the drift path end to end (make pipeline-drift)
... monitor --cutoff 2017-02-28The drift step alone: check, report, never retrain (make monitor). Used on the real data, where retraining would replace the champion
... backfillTrain once per historical cutoff, oldest first
... serve --cron "0 3 * * *"Serve the pipeline on a nightly schedule

Prefect gives each step retries, structured logs and a run history. With no Prefect server configured, it starts a temporary local one automatically.

"Needs attention" is not failure

A run is flagged needs_attention when a challenger was rejected, drift is significant, or the fairness audit fails. None of these fails the pipeline. A rejected challenger means the gate worked; drift means the world moved. Failing the run would teach whoever is on call to ignore failures. Instead there's an info alert and a line in the report.

Idempotency

An operation is idempotent if running it twice gives the same result as running it once. For a nightly job this matters: when a run fails halfway and is re-run, it must not double every subscriber's history. The pipeline leaves a populated warehouse alone, and the loaders truncate before writing rather than appending. CI runs the pipeline twice and checks the second run changes nothing and rejects the identical model it trains.

Reproducibility: DVC and params.yaml

DVC (Data Version Control) describes the pipeline as stages in dvc.yaml, each with its command, inputs, parameters and outputs:

StageDepends onProduces
simulatesimulator code; simulation paramssrc/data/warehouse.db
trainthe warehouse; feature, training, cost, calibration, fairness and profile code; features/split/model/threshold/costs/capacity/fairness paramsmodel.joblib, metadata.json, reference_profile.json, metrics.json

dvc repro re-runs only the stages whose inputs changed, and dvc.lock records the exact hash of every input and output. make metrics-diff compares the current metrics with main. Every tunable number lives in params.yaml (windows, split, model hyperparameters, costs, drift thresholds, fairness rule, promotion margin), and any of them can be overridden with an SDD_* environment variable. Changing the model is a reviewable change to one file, not an edit buried in code.

The model's own metadata records its training time, parameters, split sizes and library versions, and constraints-model.txt pins the serving image to those exact versions (Chapter 14).

Say this

"Prefect runs the pipeline as a flow (ingest, drift, train and gate, report) with retries and a nightly schedule. Drift is checked before training, because afterwards it would compare the data with itself. The pipeline is idempotent, and CI proves it by running it twice. DVC and params.yaml make every result reproducible: every setting is in one file, and only changed stages re-run."

Continuous delivery

The publish job pushes ghcr.io/markandeyavarma3-lab/subscriber-dropout-api with two tags: latest, and the commit hash. The commit tag means any deployment can be traced back to exactly the code that built it, and rolled back by deploying the previous hash. An image that failed any test can never become latest. The image is public; it can be pulled without logging in. It isn't deployed to a cloud cluster automatically (see Chapter 16), so the honest description is continuous delivery of a tested image, not continuous deployment to production.

The seventeen days CI was red

Every push from 4 to 23 September failed CI, while every test passed on the development machine, and nobody noticed. The cause: a test asserted that every file a DVC stage depends on exists on disk. train depends on warehouse.db, which is git-ignored data. It exists on any machine that has built the warehouse, and never on a fresh checkout, which is exactly what CI is. Because the test job gates the others, the warehouse, pipeline, streaming and Docker jobs hadn't run at all in that time.

It was found by running the suite on a fresh clone with CI's dependency versions, rather than in the working directory. The rule is now "exists in the repo, or is produced by a stage", which still catches the typos it was written for, and a new test proves that. Two lasting changes came out of it:

  • make demo-check now checks the latest CI run on GitHub is green.
  • The lesson: a test that passes only on your machine is not a passing test.

CHAPTER 14Deployment: Docker, Compose and Kubernetes

Eight services, one command, identical on every machine, and manifests for the step after that.

The Docker image

The Dockerfile is multi-stage. A builder stage installs dependencies and trains a model; a slim runtime stage copies only what's needed to serve. Smaller image, smaller attack surface. The service runs as a non-root user and has a built-in health check.

The image trains its own model at build time on synthetic data, because the real model file is git-ignored and a build must work from a clean checkout. For the real stack, the promoted KKBox model is mounted over it, read-only, and the service is told to load it (SDD_MODEL_SOURCE=local). Before this was fixed, docker compose up silently served the synthetic model, so the dashboard and Grafana showed a different model from the one the registry promoted.

Pinning the model's libraries

A pickled scikit-learn model should be loaded by exactly the scikit-learn that trained it. requirements.txt gives version ranges, so each rebuild pulled whatever was newest; one rebuild quietly moved scikit-learn from 1.9.0 to 1.9.1. constraints-model.txt now pins scikit-learn, pandas and NumPy to the training versions, and the demo checklist compares the running container's versions with the model's metadata.

Kubernetes

deploy/kubernetes/ holds the step after Compose:

  • Deployments for the API and the stream scorer, each with 2 replicas, CPU and memory requests and limits, and a non-root security context.
  • Probes: liveness on /health, readiness on /ready, and a startup probe so a slow model load isn't mistaken for a crash.
  • A HorizontalPodAutoscaler: 2 to 10 API replicas, targeting 70% CPU.
  • A PodDisruptionBudget: at least one API pod stays up during node maintenance.
  • A ConfigMap for settings, so the same image runs everywhere and only configuration changes.

These manifests are provided, not deployed: there's no free cluster large enough for the full stack. That's stated openly, and deploying to a managed cluster is listed as future work.
