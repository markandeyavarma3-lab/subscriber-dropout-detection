CHAPTER 5The data: from 31 GB of CSV to a warehouse

Real data from a real subscription business, cleaned with decisions that can each be defended, and stored so that any past date can be rebuilt exactly.

The source: KKBox

KKBox is a music-streaming service in Taiwan, the Asian equivalent of Spotify. Its churn dataset was released for the WSDM Cup 2018 competition on Kaggle and is public. It's anonymised: every subscriber is identified by msno, a 44-character base64 hash. There are no names, emails or anything identifying.

FileWhat it containsSize
members.csvOne row per subscriber: city, age, gender, registration channel (registered_via), registration date6.77M rows
transactions.csvPayments and plan changes: plan length in days, list price, amount paid, auto-renew flag, transaction date, expiry, cancel flag21.5M rows
user_logs.csvOne row per subscriber per day of listening: songs played to 25/50/75/98.5/100%, unique songs, total seconds392M rows

Together: 31.3 GB of CSV. Downloading it was itself a small problem: newer Kaggle API tokens (the KGAT_ kind) need "Bearer" authentication, but the installed Kaggle command-line tool only sent the older "Basic" kind and was rejected. The fix was a direct download that sent the token correctly.

Why a warehouse of events

The single most important design decision in the data layer: store immutable, timestamped events, not one pre-summarised row per subscriber.

A model is trained on the past. To build a training example "as of 1 November 2016", we need each subscriber exactly as they were on that date: their plan then, their sessions in October, their payments before then. A table of running totals ("total sessions: 412") can't answer that, because the totals already include everything that happened after November. A table of events can answer it for any date, simply by filtering on the timestamp.

The cleaning decisions, and how to defend them

1 · 2,656,043 orphan rows dropped

The transactions file references 432,623 subscribers who aren't in the members file: 18.3% of everyone who ever transacted. Two options: invent a subscriber row for each (using their first transaction as a signup date), or drop them.

They were dropped. The earliest transaction for these subscribers falls on the first day of the log, which means they almost certainly signed up before the data begins. Inventing a signup date would make long-standing, loyal customers look brand new, and the model reads "new" as risky. Losing rows is visible and countable; silently corrupting the tenure of 432,623 people is neither.

2 · Subscriber IDs widened from 32 to 64 characters

The schema originally declared IDs as VARCHAR(32); real IDs are 44 characters. SQLite ignored the limit silently. Postgres would have rejected every single row. This is the first of several bugs in this project that SQLite hid and Postgres exposed.

3 · Listening history bounded: 392M → 38.2M rows

Only sessions from 1 October 2016 to 28 February 2017 were loaded. Features look at most 30 days before a cutoff (plus all-time "last seen"), and the cutoffs used run from November 2016 to February 2017. Loading the full 392 million rows would have taken over 7 hours for data no feature uses.

4 · Negative durations clipped; prices normalised

Both covered in the mapping table above. Dropping rows with negative durations would understate activity, which the model would read as churn risk. Clipping to zero keeps the row.

Two features that learn nothing

support_tickets_last_90d and payment_failures_last_6m are always zero on KKBox: there's no customer-service data, and every payment succeeded. The model can't learn from a constant. They remain in the API because the request format requires them, and the dashboard says so openly. Be ready to explain this before you're asked.

Validation before loading: the data contract

src/data/external/contract.py checks every table before anything is written: required columns present, types parseable, values in range, IDs non-empty, and events referring to known subscribers. A --dry-run mode reads and validates everything and writes nothing. On a 30 GB export, that's the difference between finding a date-format surprise in ten minutes and finding it three hours into a half-finished load.

SQLite and Postgres: one schema, two databases

The code talks to the database through SQLAlchemy, so the same schema and queries run on both. One setting decides which: SDD_DATABASE_URL.

  • SQLite is a single file (src/data/warehouse.db, 15 GB). The project runs with no database server at all, which suits development and tests.
  • Postgres 16 runs as a Docker container in the Compose stack. It's what the demo, the dashboard and TablePlus use.

The real data was first loaded into SQLite, then copied into Postgres by src/warehouse/to_postgres.py (make warehouse-postgres). It streams each table out of SQLite as CSV straight into Postgres's bulk COPY command, in 5-million-row slices, with no temporary files. Secondary indexes are dropped during the load and rebuilt once afterwards, which is much faster than updating them on every insert. The whole copy took about 7.5 minutes (up to ~500,000 rows per second), and the row counts were verified to match SQLite exactly for every table.

Where Postgres actually runs

Postgres isn't installed on the Mac itself. It runs inside Docker, as the subscriber-warehouse container from the official postgres:16-alpine image, defined in docker-compose.yml. Its port 5432 is published to the Mac, so any client (TablePlus, the pipeline, psql) connects to localhost:5432 as if Postgres were installed normally. The data lives in a Docker named volume (warehouse-data), which survives restarts and make demo-down. MLflow's own tables live in a separate mlflow database on the same server, created by an init script, so the warehouse contains only warehouse tables.

CHAPTER 6Features without leakage

The model must never see anything it wouldn't have at prediction time. This chapter explains how the pipeline guarantees that, and the one subtle bug the guarantee exposed.

What leakage is

Data leakage is when training data contains information that wouldn't be available when the model is really used. The classic churn example: a feature like "days active in the last 30 days", computed today for a subscriber whose label comes from last month. That feature includes the very period in which they did or didn't cancel. The model looks brilliant in testing, because it's partly reading the answer, and fails in production.

Point-in-time correctness

Every training example is built "as of" a cutoff date T, with two windows that never overlap:

WindowCoversUsed for
ObservationThe 30 days before T (180 days for payments, 90 for tickets)Features, computed only from events with occurred_at < T
Prediction horizonThe 30 days from TThe label: did they cancel with T ≤ occurred_at < T + 30 days?

Nothing at or after T can reach a feature. A test in the suite (test_events_after_the_cutoff_cannot_change_features) adds future events and asserts that no feature changes. It's the most important test in the project, because if it failed, every metric would be meaningless.

The label: what "churn" means here

A subscriber churns if they have an explicit cancellation event (KKBox's is_cancel flag) in the 30 days after the cutoff. Subscribers who had already cancelled before the cutoff are excluded: they can't churn twice, and including them would fill the data with trivially-zero labels.

Know this difference

The Kaggle competition defined churn differently: no new subscription within 30 days of the current one expiring. That includes quiet lapses, not just explicit cancellations. This project's definition is stricter, which is one reason its churn rate is only about 1.5%. If an examiner knows the dataset, expect this question.

How the feature query works

One SQL query (src/features/point_in_time.py) builds every subscriber's row for a cutoff, as a chain of common table expressions:

StepWhat it computes
baseSubscribers who signed up before the cutoff (optionally capped to N, ordered by ID)
latest_stateEach subscriber's most recent lifecycle event before T: current plan, fee, auto-renew. Uses ROW_NUMBER() ordered by time, then event ID for ties
session_windowSessions in the 30 days before T: count and average duration
session_recencyThe last session ever before T. It must look across all history: a subscriber absent for 90 days has no rows in a 30-day window, and treating that as "no data" would erase the strongest signal
payment_windowFailed payments and discounts used in the 180 days before T
ticket_windowSupport tickets in the 90 days before T

Dates are passed to the query as bound parameters, and date arithmetic (tenure, days since last activity) happens in pandas afterwards. That keeps the SQL identical on SQLite and Postgres, which spell date maths differently. Tenure is measured at the cutoff, not today. A subscriber with no sessions at all gets "last active" equal to their tenure, and "last active" is never allowed to exceed tenure.

From these, src/features/build_features.py derives: tenure_months, recency_ratio (days inactive ÷ tenure), engagement_recency_score (sessions ÷ days inactive), fee_per_session, discount_dependency (discounts ÷ 6), friction_score (tickets + failures), per-month rates, and is_dormant. The plan type is one-hot encoded. The same code runs in training and serving, so the model always sees identically built features.

Splitting by time, never randomly

A random split would put rows from January into training and rows from November into testing: the model would learn from the future and be graded on the past. The test score would measure memory, not prediction. A time-based split is how the model is really used: trained on what has happened, judged on what happens next.

The bug the Postgres comparison found

After moving the warehouse to Postgres, the same training snapshot was built from both databases and compared row for row. They differed by exactly one subscriber out of 1,104.

The cause: SQLite stores dates as text. The query compared signup_date < cutoff, with the cutoff passed as a timestamp, so SQLite compared the strings '2016-12-01' < '2016-12-01 00:00:00'. As text, that's true, because a shorter string that matches the start of a longer one sorts first. So SQLite counted everyone who signed up on the cutoff day (5,850 people) as having signed up before it. Postgres compares real dates and correctly excluded them.

Impact: no future information reached any feature, because those subscribers have no event strictly before the cutoff and a later join dropped them. But they occupied slots in the capped sample, displacing real subscribers. Fix: compare the date column against a real date. A regression test was written first, confirmed to fail, and passes after the fix. After it, the two databases produced identical snapshots: every row, feature and label.

Say this

"For a cutoff date T, features only use the 30 days before T and the label only looks at the 30 days after. The windows never overlap, so the model can't see the answer. I split by time: train on November and December 2016, test on January 2017. And comparing SQLite with Postgres caught a real bug: SQLite compared dates as text and let same-day signups through. I fixed it with a test that failed first."
